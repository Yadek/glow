# Glow 1.3.0 — аудит и проект изменений

Дата: 16 октября 2026. Основа аудита: Yadek/glow, main, commit 551780f.
Статус: проект согласован 16 октября 2026; реализация 1.3.0 подготовлена. Результаты и непроверенные сценарии — в docs/validation/1.3.0.md.

## Цель

Обновить компактный интерфейс в трее в направлении iOS Liquid Glass / Windows BlurMica: стеклянная поверхность, мягкие границы и плавные элементы управления, индивидуальные карточки мониторов с их обоями, доступные настройки. Сохранить аппаратную яркость DDC/CI, индивидуальный ночной режим, общий регулятор, RU/EN, поведение после сна и горячего подключения.

Точный ранее показанный концепт недоступен: ссылка на старый чат возвращает текстовые ссылки вместо ответа с концептом. Описанное ниже оформление — предлагаемая интерпретация требований, не подтверждённая копия изображения.

## Что проверено

- C# / .NET 8, WinForms, собственная отрисовка, без стороннего UI-фреймворка. Один self-contained win-x64 exe, Inno Setup.
- BrightnessPopup уже поддерживает общий регулятор, раскрываемые карточки, ручное DPI-масштабирование, прокрутку, анимацию и привязку к трею.
- BrightnessMonitor объединяет запросы яркости и выполняет DDC-записи в фоне. NightShift управляет gamma отдельно для каждого монитора. Эти подсистемы не требуют замены ради оформления.
- RoundedPanel сейчас непрозрачен. Одного изменения цветов недостаточно для настоящего размытия фона.
- Настройки находятся в HKCU/Software/Glow; RU/EN строки — в Localization/Strings.cs.
- Текущая версия проекта — 1.2.1. Целевая версия по указанию пользователя — 1.3.0.
- README.md и README.ru.md должны обновляться синхронно. Искусственных упоминаний Claude в отслеживаемых текущих файлах не найдено. Реальную историю авторов не менять.
- Стиль коммитов смешанный: краткий английский, часто feat:, docs:, ci:. Новые коммиты должны соответствовать этому стилю, без AI-подписей и Co-authored-by.
- `dotnet build Glow.sln -c Release` успешно: 0 ошибок, 0 предупреждений. Автотестов в репозитории не обнаружено. Проверка реального оборудования и визуальная проверка приложения пока не выполнены.

## Выбор подхода

Рекомендуется сохранить WinForms и разделить дополнения на оформление окна, сервис превью обоев и сборщик статистики. Это сохраняет упаковку и существующие функции. Переход на WinUI/WPF увеличит объём миграции и риск регрессий; постоянный захват экрана увеличит нагрузку и может показывать окна вместо обоев. Для 1.3.0 эти варианты не рекомендуются.

## Предлагаемый интерфейс

Компактная шапка Glow с кнопкой настроек, общий регулятор при нескольких экранах, раскрываемые индивидуальные карточки. В каждой карточке — миниатюра экрана с обоями, название, числовая яркость, ползунок яркости при поддержке DDC/CI и отдельный ночной режим. Общие ползунки сохраняют собственное значение, как в текущей версии.

Системная светлая/тёмная тема и акцент сохраняются. Добавляются мягкие градиенты, тонкий контур и более выразительные ползунки. Настройки дают доступ к автозапуску, анимации и обновлениям, а также к отключению стеклянного эффекта и превью. Существующее меню трея сохраняется.

Для Windows 11 проверить системный DWM backdrop на реальном WinForms-окне, включая взаимодействие с Opacity и дочерними контролами. Не объявлять эффект реализованным до визуальной проверки. При неподдерживаемой системе, отключённой прозрачности, высокой контрастности или ошибке API использовать читаемую непрозрачную поверхность. Не делать весь интерфейс полупрозрачным через постоянное Opacity: это затрагивает текст и элементы управления.

## Обои

Windows предоставляет IDesktopWallpaper.GetWallpaper для конкретного monitorID. Сопоставление строить по идентификатору устройства; геометрия может использоваться как проверяемый запасной вариант. Не полагаться на одинаковый порядок перечисления мониторов в разных API. Учесть несколько обоев, слайд-шоу, однотонный фон и режим span; если точное соответствие определить нельзя, не показывать чужое изображение как правильное.

У Wallpaper Engine документирована команда getWallpaper с параметрами monitor/location. Её результат — путь активного проекта, а не поток кадров. Проверить локально наличие программы, формат ответа, соответствие мониторов и доступность статичного preview проекта. Числовой индекс без проверки соответствия недостаточен. Команды запускать только для найденного работающего экземпляра, с ограничением времени и без изменения обоев.

Предлагаемая цепочка: подтверждённое превью текущего проекта Wallpaper Engine → обои Windows конкретного монитора → нейтральное изображение монитора. Статичное превью явно отличать от живого. Отсутствующее или повреждённое изображение не должно мешать регулировке яркости. Не сканировать весь Steam Workshop.

Загрузка и уменьшение изображений выполняются вне UI-потока; COM-вызовы — на корректно инициализированном потоке. Ограничить размеры и число закэшированных изображений, освобождать GDI-ресурсы и файлы. Отбрасывать устаревшие результаты после закрытия окна или изменения конфигурации экранов. Не добавлять постоянный опрос и запись миниатюр на диск при скрытом popup.

Живой захват не входит в гарантии 1.3.0. Документация Wallpaper Engine не подтверждает универсальный API кадров. Его можно включить только после отдельной проверки качества, нагрузки и совместимости; при неудаче остаётся описанный fallback.

## Статистика GitHub

Ежедневный GitHub Action и ручной запуск собирают stars, forks и сумму download_count всех assets всех страниц releases, включая prereleases. Подпись поясняет, что скачивания относятся к файлам релизов, а не к уникальным пользователям или установкам.

История хранится в JSON в отдельной ветке статистики. SVG-график и сводка генерируются из этих данных и встраиваются в оба README. Отдельная ветка предотвращает запуск существующего тяжёлого build/installer pipeline на каждом обновлении статистики; дополнительно потребуется исключить эту ветку в текущем build workflow.

Stars, forks и downloads получают реальные дневные снимки начиная с первого запуска. Удаление релиза или файла может уменьшить текущую сумму; не исправлять такой результат искусственной монотонностью. Первый график с одной точкой должен честно показывать один замер.

Traffic views/clones доступен за 14 дней при необходимых правах. Новые ответы сливаются с историей по UTC-дате, а не суммируются с перекрывающимися ответами. Ошибки доступа и пропуски — null/«нет данных», не ноль. Уникальных посетителей за разные дни не складывать в показатель уникальных за весь период.

Обычный GITHUB_TOKEN использовать для публичных метрик и записи ветки. Traffic — только если доступен отдельно настроенный repository secret с подходящими правами; отсутствие секрета не мешает остальным метрикам. Подключение GitHub в чате не создаёт автоматически секрет для Actions. Секреты вводятся только через интерфейс GitHub, не в переписке и не в коде.

Запись ветки должна быть сериализована, без force push чужих изменений. Ошибка сети не должна затирать валидную историю. Первый запуск создаёт данные, README до него сообщает об ожидании первого замера.

## Порядок реализации и проверки

1. После согласования проекта подготовить подробный план и изолированную ветку разработки.
2. Добавить сервис обоев и тесты сопоставления мониторов, ошибок, fallback и устаревших результатов.
3. Обновить карточки, оформление, настройки и RU/EN, сохранив обработчики яркости и ночного режима. Проверить клавиатуру, высокую контрастность и отключение анимации.
4. Добавить сборщик статистики и тесты пагинации, слияния traffic, пропущенного доступа, одиночной точки, отсутствующих и повреждённых данных; встроить SVG в оба README.
5. Установить версию 1.3.0, собрать и опубликовать локальный self-contained exe для проверки. Проверить DPI 100/150/200%, одну/несколько карточек, переполнение по высоте, светлую/тёмную тему, fallback оформления и обоев.
6. Проверить DDC/CI, gamma, сон/возобновление и hot-plug на доступном оборудовании; явно перечислить то, что не удалось проверить. Не менять яркость оборудования без необходимости проверки и согласованного сценария.
7. Проверить diff, авторство и отсутствие AI-трейлеров. Коммит и push — только после подтверждения прав GitHub и проверок. Публикацию бинарного релиза и тег v1.3.0 выполнять отдельным завершающим действием после готовности версии.
